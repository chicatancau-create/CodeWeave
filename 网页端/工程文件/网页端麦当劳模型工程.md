## 2. 逐条实现说明

### 2.1 顶部一体化（去掉分层）

**原先有几层**（实测 546×1146 视口，代码模式下从上到下）：
顶栏（面包屑 + 课名 `contextTitle`）→ 资料库同步横幅 `.desktop-vault-settings`
→ 资料来源状态条 `.content-source-banner` → 工作区页头 `.learning-header`
→ 分区导航 `.cw-pane-nav` → 代码/画布。**五条横带**，用户说的「明显的分层」就是它。

**改法**（全部只改呈现，DOM 一个元素不增不减）：

| 文件 | 规则 | 作用 |
|---|---|---|
| `src/styles.css` | `.app-shell:has(.cw-workspace.is-code-mode) > .sidebar / .shell-decor / .topbar { display: none }` | 收起侧栏、装饰框、顶栏 |
| 同上 | `… .content-wrap > .desktop-vault-settings`、`… .content-wrap > .content-source-banner { display: none }` | 收起那两条**工作区之外的**状态条 |
| 同上 | `… .main-content { padding-top: 0 }` | 还回顶栏占的 68px（`--topbar-h` 64 + 4） |
| `learning-workspace-view.css` | `.cw-workspace.is-code-mode .learning-header / .cw-pane-nav` 收窄间距、副标题让位 | 页头与导航合成一条窄带 |

**为什么这几条写在 `styles.css`**：那两条状态条是 `.cw-workspace` 的**兄弟节点**，
而 `learning-workspace-view.css` 的棘轮要求每个选择器都带 `.cw-workspace`——兄弟选择器
满足不了。外壳（侧栏/顶栏/内边距）本来也只归 `styles.css`。

实测结果：五条横带 → 一条（页头「返回 + 课名 + 三个动作」+ 分区导航），
`pageScroll: 0`，工作区从视口顶端起算。

### 2.2 一步一步显现（画布）

**用户要的行为**：
- 进入主函数先在画布**正中**出现；
- 点「下一步」时，上一步**不删**、移到合适的位置，新的一步弹出来，数据跟着显示；
- 「继续运行」一步到底但**逐条弹出**；「单步执行」点一下动一下；
- 动画要流畅。

**改法**（三处，缺一不可）：

1. `src/engine/stage-layout.ts` — `LaidNode` 增加 `enterDx` / `enterDy`：
   这一格的中心到**画布正中**的位移。画布尺寸是这一层的产物，组件拿不到「正中」在哪；
   而且这是纯算术，能单测，不用靠肉眼看截图。尺寸的计算顺序因此提到 `nodes` 之前。
2. `src/components/run-stage.tsx` — 每个 `<g>` 把位移写成 CSS 自定义属性
   `--rs-enter-dx` / `--rs-enter-dy`（每格不同，只能用内联 style，类名表达不了数值）。
3. `src/components/run-stage.css` —
   - `g.rs-node.is-todo { opacity: 0 }`：还没走到的不画，**但留在 DOM 里**
     （它是列表的一项，也是「还有几步」的证据；删掉元素会让读屏读到一份不完整的程序）；
   - `@keyframes rs-node-enter`：从画布正中（位移 + `scale(.84)`）飞回自己的格子；
   - `g.rs-node.is-done { transform: none }`：上一步停在原地——「移到合适的位置」
     是动画的**终点**，不是另一段动画；
   - `g.rs-edge.is-idle { opacity: 0 }`：指向空位的箭头不画。

**为什么用 `transform` 而不是改 `x`/`y` 属性**：transform 走合成层，改 `x`/`y` 每帧都要
重排几何；而且 transform 不吃文档流，不带动旁边已经画好的格子。

**动效纪律**：本文件原先写着「不含 `@keyframes`」。这条**按用户要求改了**，并已在文件头注明。
保留的动效只有这一条，播放一次、无 `infinite`、静态截图仍读得出状态；
`prefers-reduced-motion` 与 `.reduce-motion` 两条降级路径照旧全停。

**按钮文案**：`runtime-controls.tsx` 的空闲档从「运行代码」改为「开始运行」，
与暂停档「继续运行」相对（用户原话点名了这两个词）。

### 2.4 三个运行入口各归其位（开始 / 继续 / 单步）

用户原话：

> 「点击『开始运行』时，中间就会出现最开始的内容，比方说『进入主函数』……
> 点完之后，可以点击『继续运行』。因为我说的是『继续运行』，所以是一步到底的运行。
> 内容要一步一步地弹出来，而不是已经完全显现出来。
> 点『单步执行』的话，就是一步一步地弹，我点一下它动一下。」

改版前 `handleRun` 第一次点击就是 `startRun('running')`——**一路播到末态**，
用户第一眼看到的就是 15/15，等于「一步一步」当场落空。现在三个入口各管一件事：

| 入口 | 行为 | 实现 |
|---|---|---|
| 运行条「开始运行」 | 只落到**第一拍**就停住 | `handleRun` → `startRun('paused')` |
| 运行条「继续运行」 | 逐拍推进到末态（850ms 一拍） | `resumeRun()` → `setRunStatus('running')` |
| 运行条「单步执行」 | 点一下走一拍，状态停在 paused | 既有 `handleStep`，未改 |
| 画布「播放」 | 第一下**直接放到底** | 新拆出的 `handlePlay` → `startRun('running')` |

**为什么要拆出 `handlePlay`**：画布那枚按钮的字面意思就是「播放」，「放一遍」是它的语义；
运行条的「开始运行」是「走到第一步给我看」。两者共用一支函数，必有一个名不副实。
拆开后 `LearningWorkspaceView` 新增一个 `onPlay` prop，`RuntimeTrace` 的
`onTogglePlay` 收它（原先收的是 `onRun`）。

**顺带堵上的一个洞（`resumeRun`）**：减少动效档下，`startRun` 里那条 `still` 判定
只在**新跑一次**时拦得住（`reducedMotion && nextStatus === 'running'`）。
「继续运行」这条路径不经过 `startRun`，原先直接 `setRunStatus('running')`，
于是同一个开关会出现「第一次点不播、第二次点开始播」——等于绕过用户自己的设置。
`resumeRun` 把这一档也问一遍 `reducedMotion`：命中就直接落到末态（结果一条不少，
只是不逐帧放）。这条路径在改版前不存在（那时第一下就是 `running`），
是「开始运行停在第一拍」之后才露出来的。

**实测（546×1146 视口，`Java 的第一个循环`，15 拍）**：

| 操作 | 结果 |
|---|---|
| 点「开始运行」 | `01 / 15`、程序开始、5 个未到节点 `opacity: 0`、按钮变「继续运行」 |
| 点「继续运行」 | 逐拍推进到 `15 / 15`、程序结束 |
| 重置 → 单步 ×3 | 0 节点 → `01 / 15` → `02 / 15` → `03 / 15`，上一步的节点停在原地变 `is-done` |

### 2.3 代码内容占满整页

`learning-workspace-view.tsx` 的 `codeMode` 初值从 `false` 改为
`Boolean(lesson.code) || lesson.flow.length > 0`——**有代码或有画布的课一进来就是全屏**；
纯阅读单元保持普通版式（那种课铺满整屏是空场子）。

换课时按新课重算默认档，用**渲染期重置**（`codeModeLessonId !== lesson.id` 就重置）而不是
`useEffect`：换课的这一次渲染里 `lesson.id` 已经是新的，用 effect 会先按旧值画一帧
（全屏闪一下再收回）。同一文件对 `evidenceLessonId` 用的是同一写法。

左上角的「返回」是页头本来就有的 `.back-button`，不需要新造。

### 2.5 全站一屏化（外壳永不滚，超长内容进小框）

用户从第一次反馈到最近一条都在说同一件事：

> 「登录进去之后点击『学习』，能不能让它一屏化？所有页面我不想要上下滑动了。」
> 「如果里面需要上下滑动，也不要滑动总界面，你给它一个小框，我去看小框里面的滑动。
> 外面的总界面你总是滑动干嘛？你根本看不到。」

**病灶**：`src/design/desktop-theme.css` 第 64 行
`.app-shell .content-wrap { height: 100%; overflow: auto }` —— 整页滚动就出在这里。
实测 1480×940（`content-wrap` 可视高 872）：首页内容 1784px 要滑 912、挑战页 438、分析页 912。

**改法**（只改呈现）：

| 范围 | 做法 |
|---|---|
| 外壳 | `.content-wrap { overflow: hidden; display: flex; flex-direction: column }` —— 外壳永不滚 |
| 首页 | 科目条/页头/工具条钉住；课程网格与右栏各自 `overflow-y: auto` 成为小框 |
| 挑战页 | 页面根 `.challenges-view` 自己成为小框；编辑器与提交历史各给 `46svh` 上限 |
| 分析页 | 同上，页面根 `.cw-analytics` 成为小框 |
| 其余页 | 页面根同样吃满剩余高度并内部滚动 |

`min-height: 0` 与 `flex: 1 1 auto` 必须成对出现——flex 子项默认 `min-height: auto`，
不给 0 的话按内容撑开，`overflow-y: auto` 永远不触发。

**实测（1480×940，六个视图）**：`docScroll: 0`、`content-wrap over: 0`；
超长内容全部进小框（首页网格内滚 750、挑战页内滚 445、分析页内滚 750）。
1280×800 与 1024×768 复测同样 `pageScroll: 0`。

### 2.6 首页流动科技风背景（找回被关掉的那一层）

用户从最初就点名要「首页流动科技风背景」。那套动效**一直写好了**——`src/styles.css`
的 `.shell-decor::after` 七层背景 + `cw-bg-drift`（34s）+ `cw-bg-sheen`（26s）两条无限循环。
但 `desktop-theme.css` 第 65 行 `.app-shell .shell-decor { display: none }` 整层关了它：
实测首页 `decorDisplay: "none"`，样式写完了没被挂上。

**为什么当初关掉**：那层 `z-index: var(--z-decor)=10` 高于内容列（1），
而它的 `::after` 带一块不透明底色（`--ds-canvas-deep` #03050a，要压住 `--page`
才能让光晕「从背景里透出来」）。原样放开会盖住正文。

**改法**：放开的同时把它压到内容之下（`z-index: -1`）。它在 `.main-content`
（`z-index: var(--z-content)`）的栈上下文里，`-1` 位于正文之下、页面背景之上，
于是光晕与网格在字后面流动。既有两条开关（`.is-immersive` 与代码模式）照旧生效——
**工作台那一屏仍然没有背景**（§5.3 第 1 条：编辑器与画布低动态）。

### 2.7 文字流程图彻底退场（运行前也走画布）

用户原话：「你现在的画布效果一直就是个文字而已。」

之前只有**运行之后**画布才接棒，**运行前**同一位置露出的仍是那条文字拍轨
（`.flow-chart`，「01 进入 main / L1 / 场景」）——而运行前恰恰是第一眼看到工作台的时候。

**改法**：新增 `engine/run-stage-model.ts` 的 `skeletonStageFrame(steps)`——
把「这段程序有哪几步」按图形画出来，每个节点都是未走到（`ordinal: null` 画 `--`、
`cells: []`、`caption: ''`、`outputLines: []`），**一个假值都不编**。
上层 `stageFrameAt(...) ?? skeletonStageFrame(...)`；`RunStage` 据此加 `.is-skeleton`
（未到节点显形、指针不画、计数器改说「尚未运行」而不是矛盾的 `01 / 00`）。
文字拍轨自此在任何状态下都不再出现在屏幕上。
