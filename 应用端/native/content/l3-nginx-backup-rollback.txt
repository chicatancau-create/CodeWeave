Nginx 反代、备份与回滚
上线只是开始，回滚才是底线

【来源】
CodeWeave 内置课程快照；学习进度由当前账户证据决定。

【运行环境】
外部环境 · Nginx + Linux

【目标】
独立完成 Nginx 反代接入、一次带备份的发布和一次成功的回滚演练。

【先备知识】
l2-docker-compose

【讲解】
Nginx 反代统一入口：静态资源直出、API 转发、TLS 终结。
发布前备份 + 版本命名，回滚 = 恢复备份 + 重启，全程不超过几分钟。
发布后验证清单（健康检查、核心接口、错误率）先于“宣布成功”。

【例子与反例】
正例：带日期的备份文件 + 一页 runbook，任何人都能执行回滚
反例：“直接覆盖再看看”，出问题时旧包已不存在
解释：不可回滚的发布是高风险操作

【示例代码】
# nginx 反代（节选）
# location /api/ { proxy_pass http://127.0.0.1:8080; }
# 发布流程：
# cp app.jar app.jar.bak-$(date +%F)   # 备份
# mv app-new.jar app.jar && systemctl restart myapp
# 回滚：cp app.jar.bak-日期 app.jar && systemctl restart myapp

【理解要点】
回滚方案必须在第一次部署前写好：没有“退路”的发布是把用户当试验品。

【跟做】
配置 Nginx 反代 /api/ 到应用并验证。
执行一次带备份的版本发布，按清单逐项验证。
人为让新版失败，执行回滚恢复服务。

【独立练习】
独立编写一页 runbook：发布步骤、验证清单、回滚步骤。

【变式】
Nginx 配置 gzip 与静态资源缓存头，用 curl 验证生效。

【项目任务】
runbook 与备份策略是 L 阶段验收交付手册的必备章节。

【常见错误】
改 nginx.conf 忘记 nginx -t 检查就 reload
备份与正式包在同一块盘，盘坏全丢

【运行方法】
本地/服务器 Nginx + systemctl（真实环境）

【完成标准】
反代生效、发布与回滚演练各一次成功，runbook 可交付。

【验收条件】
反代接入并验证
发布含备份与验证清单
回滚演练成功且限时

【证据清单】
nginx 配置
发布与回滚日志
runbook 文件
