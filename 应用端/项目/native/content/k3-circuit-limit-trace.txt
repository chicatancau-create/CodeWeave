熔断、限流与调用链
故障在这里停下，而不是扩散

【来源】
CodeWeave 内置课程快照；学习进度由当前账户证据决定。

【运行环境】
外部环境 · Spring Cloud

【目标】
独立演示一次熔断降级与一次限流拒绝，并用日志把调用链串起来。

【先备知识】
k2-gateway-config

【讲解】
熔断器三态：关闭（正常）→ 打开（直接走降级）→ 半开（试探恢复）。
限流在网关或服务端限制速率，保护下游不被突发流量打垮。
traceId 贯穿网关与各服务日志，是排错时唯一可靠的线索。

【例子与反例】
正例：B 挂掉后 A 返回友好降级文案，恢复后自动闭合
反例：B 挂掉后 A 的线程池被拖满，整个服务雪崩
解释：故障隔离防止雪崩扩散

【示例代码】
@CircuitBreaker(name = "serviceB", fallbackMethod = "fallback")
public String call() {
    return restClient.get().uri("/api/data").body(String.class);
}
public String fallback(Throwable t) {
    return "service-b 暂不可用，请稍后重试";
}

【理解要点】
熔断保护调用方，限流保护被调方，链路追踪把三次跳转串成一条可解释的路径。

【跟做】
给 A→B 调用加熔断与降级方法。
停掉 B 连续调用，观察打开/半开/闭合三态日志。
网关配置限流，用压测脚本触发 429。

【独立练习】
独立在网关与两个服务间传递 traceId，串出一条完整调用链日志。

【变式】
调整熔断阈值（失败率/窗口），对比行为差异并记录。

【项目任务】
熔断演示是 K 阶段验收的压轴证据；调用链日志是答辩的核心材料。

【常见错误】
降级方法签名不匹配导致熔断不生效
只压测不看日志，结论全靠猜

【运行方法】
本地多服务 + 压测脚本（真实故障注入）

【完成标准】
三态日志齐全，限流触发 429，调用链可按 traceId 串读。

【验收条件】
熔断三态可观察
限流触发并返回 429
traceId 串联至少两跳日志

【证据清单】
三态日志
429 响应记录
调用链示意
