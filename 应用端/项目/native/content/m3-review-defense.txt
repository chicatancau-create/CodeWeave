Bug 修复、答辩与延迟复测
能解释的交付才算完成

【来源】
CodeWeave 内置课程快照；学习进度由当前账户证据决定。

【运行环境】
外部环境 · 文档 + 演示环境

【目标】
独立完成 3 个 Bug 的完整修复记录，并准备答辩三问的书面回答。

【先备知识】
m2-timebox-mvp

【讲解】
Bug 记录五要素：现象、复现步骤、根因、修复、复测——缺复测等于没修。
答辩的语言是“权衡”：为什么用 A 不用 B，代价是什么。
延迟复测（1/3/7 天后重做核心题）检验的是留存，不是当时会做。

【例子与反例】
正例：根因写到“N+1 查询导致列表接口 2s”，附修复前后耗时
反例：根因写“代码有问题，已修复”
解释：不可复现的根因说明定位过程是猜的

【示例代码】
# 答辩三问准备：
# 1. 你的架构为什么这样分层？
# 2. 遇到的最难的 Bug 是什么，怎么定位的？
# 3. 如果再有 2 小时，你优先做什么，为什么？
# Bug 记录模板：现象 / 复现步骤 / 根因 / 修复 / 复测结果

【理解要点】
答辩考的不是功能数量，而是每个决策能否被解释；Bug 修复记录就是你的深度证明。

【跟做】
从 M2 的验证清单收集 3 个真实 Bug 并按五要素记录。
逐个修复并在演示环境复测。
写答辩三问的回答并演练一遍。

【独立练习】
独立为其中一个 Bug 写“错误修复 vs 正确修复”的对比说明。

【变式】
把 Bug 清单里的两个知识点排进 1/3/7 天复测计划（本平台复测系统）。

【项目任务】
本单元输出是 M 阶段验收的答辩材料与最终提交物。

【常见错误】
只修不复测，回归时旧问题复发
答辩背功能清单而不讲权衡

【运行方法】
演示环境 + 文档（人工产出）

【完成标准】
三个 Bug 五要素齐全且复测通过，答辩三问有书面回答。

【验收条件】
3 个 Bug 五要素记录完整
复测全部通过
答辩三问书面回答就绪

【证据清单】
Bug 修复记录
答辩问题回答
复测计划
