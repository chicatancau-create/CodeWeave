> 当前审计入口（2026-10-05）：[审计修复记录](../审计修复记录.md)。MSVC/SDK/Qt 6.8.3 已安装并完成环境核验。根目录 EXE 仍是原生 C++23/Win32 回滚入口；Qt 版本必须通过分阶段验收后才允许替换，安装器仍排在 UI 验收之后。旧启动链记录已移入备份区。

## 项目定位

应用端目标是可独立构建、安装、运行、升级和卸载的 Windows 原生桌面软件。Qt 6 + Qt Quick/QML + C++ 预览链已完成 U1–U4 与 B0–B3 的内部验收；根入口仍保留 C++23/Win32 便携 EXE 作为回滚基线。正式公开发布仍受干净 Windows、DPI/IME/UIA、同机性能和 Qt LGPL 材料门禁约束。

本次状态修订：2026-10-05。范围仅限应用端；原生重构与真实隔离验证已执行，Qt/QML 基础壳和可重复部署目标已建立，尚未替换根 EXE，未操作真实用户数据、未上传发布。网页端、移动端和其他端的优先级、代码与发布路线不变。

## 优先级

1. **当前最高：Qt Quick/QML 应用端重构**。先完成工程文件、响应性基线和后端任务边界，再建立 Qt 基础壳；保留 C++ 核心与 Win32 回滚入口。
2. **随后：按功能矩阵恢复旧 UI 的行为和视觉**。本轮先提供窗口、导航、状态模型、主题参数和可替换组件骨架；精细视觉复刻由后续 UI 实施者逐页完成，不把占位骨架宣称为完成品。
3. **最后：完整检查与普通安装包**。内部预览安装器已经生成并完成隔离安装、升级、卸载和数据保留验证；正式公开发布仍需完成外部环境和许可证门禁，并另行请求发布授权。

“换 UI”是更换呈现框架，后端继续 C++。QML 是声明式语言，含 JavaScript 表达式/运行时；它没有浏览器 DOM，也不要求 Node，但不能称为“全 C++、所有逻辑都原生编译”。现有 Win32 后端与入口是基线；Qt 迁移已获用户授权并开始实施；当前 U2 状态与验证见后端工程 14.14。

## 本轮执行计划（2026-10-05）

### 目标与完成定义

本轮目标是把应用端从“Win32 可回滚产品 + Qt 方案”推进到“可独立构建的 Qt 基础壳 + 稳定后端契约 + 内部预览安装器”，同时保留可运行的 Win32 入口。当前内部预览已完成；正式公开发布仍以外部环境门禁为准。

- 工程文件明确记录范围、所有者、禁止事项、回滚点和验证命令；
- U0a 原始耗时样本来自隔离合成夹具，写入 `应用端/evidence/`，不含真实账户或工作区；
- U0b 后端任务契约通过核心回归，长任务不会把 UI 线程当作工作线程；

- Qt 基础壳只负责窗口、主题、导航和 DTO 展示，不写文件、不启动进程、不判定学习完成；
- 根目录 `CodeWeave.exe` 在 Qt 通过完整门禁前保持 Win32 版本。

## 关键边界

目标版本只从应用端自有源码和锁定的第三方依赖构建；不读取网页端源码、`dist`、网页后端 runtime，也不通过嵌入旧 renderer 延续产品主体。共享教学资料只能作为有版本的数据格式或用户选择的内容库输入，不成为跨端可执行代码依赖。

应用端拥有原生界面适配和本地业务实现。UI 仅提交命令、显示状态和编辑未保存草稿；账户、正式进度、存储事务、内容权限与执行策略由后端拥有。必要的原生 UI 接入属于完成独立应用的依赖任务，由后端定义契约，界面负责人实现，不改网页端以配合迁移。

本轮不改认证规则、数据结构或用户资料；这些属于后续实施中的专项设计与审批边界。真实数据必须先只读盘点和备份验证，再由用户确认迁移。不得删除旧工程、备份或现有 EXE来证明“去耦合”。

## 第一性原则与目标形态

- 用户需要的是稳定的学习、编辑、运行与进度管理流程；原网页路由、Cookie、HTTP origin 和框架不是业务需求。
- 系统应从桌面窗口 → 应用服务 → 领域模型 / 数据仓库 / 执行工作进程组织依赖；磁盘读写和长任务不能阻塞界面。
- 日常安装和启动不要求 Node、pnpm、开发服务器、浏览器或人工配置端口。系统运行库由安装器处理；具体课程需要的编译器须明确预装、随包许可或按需配置策略。
- 安装后提供开始菜单入口、应用 EXE、版本信息、正常卸载和可验证升级；程序目录与可写用户数据目录分离。安装包是新的正式交付目标，现有 portable EXE 不替代安装包验收。

## UI 正式技术路线与性能门禁

当前 Win32 控件界面保留为可回滚基线。后续 UI 重建的正式首选方案是 **Qt 6 + Qt Quick/QML + C++**：Qt Quick 在 Windows 上通常使用 Qt Quick Scene Graph 和 D3D11 渲染路径，QML 适合复刻黑色画布、轨道、渐变和动画；现有 `codeweave-core` 继续作为唯一业务事实源。本轮评估结论：该路线适合本项目，已选为下一代应用端正式首选方案。基准测试用于实现优化与交付验收，不悬置选型；没有实测仍不得宣称“绝对最快”。依据链接见本节末尾。

选型决定 ADR-UI-01（2026-10-05，首选路线已确定，未实施）：

| 方案 | 本项目决策与依据 |
| --- | --- |
| Qt Quick/QML + C++ | 正式首选；原生绘制、自定义视觉和 C++ 复用适合现状，存在内存、适配和部署成本 |
| Electron/Tauri/WebView2 | 按用户无浏览器引擎约束排除 |
| RmlUi | 保留备选；RCSS 是 CSS 子集，未逐项验证，不能承诺原 CSS 大量直接复用；编辑器、IME、无障碍需额外验证 |
| Win32 + Direct2D/DirectComposition | 保留性能对照；维护自绘文本/交互成本高，不能先验断言绝对更快 |
| Flutter/Avalonia/Compose | 本期不采用，避免增加语言和互操作维护；不推导其性能必然较差 |
| WinUI 3 | 本期不采用以控制范围；支持 unpackaged 部署，不是强制 MSIX，也没有本项目证据证明慢于 Qt |
| ImGui/egui | 本期不采用；文档编辑、无障碍和视觉复刻适配成本需逐项评估，不按框架名判定不可能 |

Qt 与 C++ 核心同语言有利于复用，但需要 QObject、列表模型、线程切换与 DTO 适配，并非“零胶水”。Windows API 在核心中不妨碍 Windows 上使用 Qt；跨平台不是本轮前置目标。

### Qt 路线的硬性约束

1. 使用 `QQuickView`/`QQuickWindow` 作为顶层窗口，不使用 `QQuickWidget` 作为性能路径。Qt 官方说明 `QQuickWidget` 会关闭 threaded render loop，并增加离屏 render pass；如果确需 QWidget 编辑器，必须单独测量其代价。
2. C++ 通过明确的 `QObject` facade 暴露只读模型、命令和信号；QML 不直接打开文件、启动进程、写账本或决定学习完成。
3. QML 只负责布局、视觉状态、动画和用户输入；账户、草稿、执行、进度、证据、迁移和备份仍归 `codeweave-core`。
4. QScintilla 不能直接当作“免费且天然适配 QML”的答案：其官方许可为 GPLv3 或商业许可，并且它是 QWidget 控件。引入前必须完成许可证选择、动态链接/源代码义务审查和 QWidget/QML 性能实测。未完成前不得加入依赖。
5. Qt Canvas Painter 在 Qt 6.11 许可页面列为 GPLv3 模块。当前低成本闭源路线不得直接依赖它；只有取得合适商业许可或确认产品许可边界后才重新评估。
6. 采用 LGPL Qt 时，本项目选择动态链接 Qt（静态链接并非一概违法，但合规与重链接交付更复杂，本期不采用）。逐模块记录确切版本/许可，提供许可证、通知、实际使用 Qt 库对应源码及修改、替换/重链接所需信息，不能禁止为调试库修改所需的逆向工程；适用时提供安装信息并验证替换能力。自有业务代码不因满足 LGPL 就必须公开。不得把 GPL-only 模块混入包，也不认为“动态链接”一个动作就完成全部义务。

### 迁移前固定性能基准，按预算验收

在同一台 Windows 机器、同一 MSVC Release 配置和同一内容快照下，建立当前 Win32 基线，再做最小 Qt 原型：空窗口、74 项滚动列表、代码编辑区域、一个发光动画。先分别运行等工作负载场景（空窗口、同数据列表/编辑器），再评估 Qt 特有动画的增量；不能把功能不同的两个 EXE 当成同口径胜负。至少重启后首次启动 5 次、热启动 10 次，交替顺序，保留原始样本；未重启/未控制缓存只能称 fresh-profile。5 次尾部样本不足以作稳定 P95 结论，必须披露样本量。记录 P50/P95：

- 可见窗口时间、进程总工作集、启动 CPU 和关闭时间；
- 60 Hz/120 Hz 动画帧间隔、滚动期间丢帧和主线程阻塞；
- 中文输入、连续编辑、撤销/重做的输入响应；
- 备份/恢复、scrypt 登录、内容读取期间窗口是否保持可交互；
- 发布目录大小、Qt 运行库体积、启动依赖和崩溃退出清理。

测量脚本、机器信息、EXE hash 和原始样本放 `应用端/evidence/qt-ui-benchmark-*.json`；没有原始样本不得写“性能提升”。初始工程预算（待 U0 记录目标硬件后冻结，不是实测结论）：60 Hz 场景呈现帧间隔 P95 ≤ 20 ms、超过 33.3 ms 的帧 < 1%；120 Hz 仅对实际支持硬件单列验收。编辑键入到呈现 P95 ≤ 50 ms，主线程任务 P95 ≤ 16.7 ms，取消确认 ≤ 100 ms；工作集/可交互启动若相对同负载基线增加超过 20% 或包增加超过 50 MiB，必须解释并由用户接受取舍，不能直接宣称提速。动画渲染结束不是屏幕呈现：优先使用 PresentMon/ETW 呈现数据，Qt Profiler 辅助定位，工具不可用须标注。若 Qt 原型不满足预算，先定位线程、模型、渲染或编辑器瓶颈并优化，不擅自更换路线；保留 Win32 入口直至 Qt 验收通过。必须改变范围或放宽预算时记录证据交用户决定。

## 部署与实现约束

当前 `native/CMakeLists.txt` 使用 `/MT`；Qt 官方 MSVC 二进制通常使用 `/MD`。U1 须锁定同架构、工具链、CRT 与 Release/Debug 组合；Qt 目标及相连核心在独立构建树中统一 `/MD`，不得直接混链接现有 `/MT` 对象，也不承诺旧 EXE 的运行库条件继续成立。

仅在获准实施后新增可选 Qt CMake 目标；Qt OFF 时既有核心与 Win32 必须仍可构建。U1 的 `codeweave-qt-deploy` 目标调用 `native/ui-qt/deploy-qt.ps1`，固定传入 Qt SDK 的 `bin` 与 QML 源目录，并使用 `windeployqt --release --compiler-runtime --no-translations --qmldir` 收集 Qt DLL、`platforms/qwindows.dll`、QML imports 和编译器运行库。脚本在结束时检查 `Qt6Core/Gui/Qml/Quick.dll`、平台插件和 `qml/QtQuick`，不通过就失败；它不替换根 EXE，也不接触用户数据。现有 `package-native.mjs` 只复制单 EXE 与内容，不能直接打 Qt 包，需显式扩充受审查清单，签名后生成所有文件 hash。禁用 WebEngine/WebView，动态库替换不能被应用固定 Qt hash 机制阻止。

干净 Windows x64（无 Qt/开发 PATH）验证启动、插件发现、中文路径、100/150/200% DPI、输入法、无障碍、GPU 不可用/RDP 降级、升级卸载保留数据。软件渲染降级结果单列；不能用更换后端掩盖动画性能失败。原 Win32 UI 自动化依赖 HWND/控件 ID，Qt 阶段必须增加 Qt Quick Test/可访问性驱动的真实窗口流程，旧 smoke 通过不代表 Qt 已测。
